## How it was produced, and why not the obvious way

The documented way to do this is `lake -R -Kenv=dev build DirichletTruncations:docs`. **Do not**:
doc-gen4 documents the entire *import closure*, and since these files `import Mathlib` that means
all 8268 Mathlib modules — hours of work and gigabytes of HTML, to obtain ten pages.

Instead, doc-gen4's `single` subcommand documents one named module into a SQLite database, and
`fromDb` renders HTML for whatever is in that database. Mathlib is never documented at all:

```sh
B="https://gitlab.liu.se/jansn19/lattice-line-covers/-/blob/main/lean"
lake exe doc-gen4 single LatticeLineCoversLean docs.db "$B/LatticeLineCoversLean.lean"
for m in Basic MainRecursion Sieve Steering Direction Density Family; do
  lake exe doc-gen4 single "LatticeLineCoversLean.$m" docs.db "$B/LatticeLineCoversLean/$m.lean"
done
lake exe doc-gen4 single Challenge docs.db "$B/Challenge.lean"
lake exe doc-gen4 single Solution  docs.db "$B/Solution.lean"
lake exe doc-gen4 fromDb .lake/build/docs.db LatticeLineCoversLean Challenge Solution
```

Two traps worth recording. **`single` writes its database relative to the build directory** while
**`fromDb` takes a plain path** — pass `docs.db` to the first and `.lake/build/docs.db` to the
second, or `fromDb` silently reads an empty file and dies with `no such table: declaration_args`.
And **the `sourceUri` argument is used verbatim**, not as a base to which the module path is
appended, so it must be the full URL of that specific `.lake` file, given afresh for each module.

Requires doc-gen4 pinned to the tag matching the toolchain — `v4.33.0-rc1` here. Its `main` branch
tracks a newer Mathlib whose cache is not local, which forces a from-source build.

Cross-references into Mathlib are not resolvable (Mathlib is not in the database), so identifiers
like `Nat.Prime` render as plain text; the navigation's Mathlib entry has been rewritten to point at
the public mathlib4_docs site.
